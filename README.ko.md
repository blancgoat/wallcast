# Wallcast

[English](README.md)

Windows용 작은 라이브 바탕화면 앱. 캡처보드나 가상 카메라 — 또는 동영상 파일 — 를 모니터 하나의 바탕화면 아이콘 뒤에 표시합니다.

## 사용

1. `artifacts/Wallcast/Wallcast.exe` 실행.
2. 기본값인 **캡처보드 / 가상 카메라**에서 장치를 선택하거나, **동영상 파일**에서 파일 선택.
3. 출력 모니터를 선택하고 **바탕화면 적용**.
4. **중지**하면 기존 배경이 다시 보입니다. 창의 X는 트레이로 숨기며, 완전 종료는 트레이 메뉴의 **종료**입니다.

동영상은 원본 모양을 유지하며, 이음매 없이 반복됩니다. 플레이어를 멈췄다 다시 시작하는 대신 입력 자체를 반복시키므로, 한 바퀴 돌 때마다 0.2초쯤 바탕화면이 드러나던 현상이 없어졌습니다. 두 입력 모두 같은 방식으로 화면에 배치할 수 있습니다. [배치](#배치) 참고. 둘 다 기본 음소거이며 해제할 수 있습니다. [소리](#소리) 참고. 캡처 버퍼 값은 DirectShow 큐 용량을 정하는 기준이며 정확한 지연 시간이 아닙니다. 큐 용량은 장치가 내보내는 형식의 프레임 크기로 계산하므로, 같은 값이면 해상도가 올라가도 담기는 프레임 수는 같습니다. 화면 출력은 가장 최근 프레임을 사용하며, 프레임이 도착할 때마다 바로 표시합니다.

### 캡처 설정

| 설정 | 선택지 / 기본값 |
| --- | --- |
| 영상 형식 | **NV12**, YUY2, UYVY, RGB24, MJPEG |
| 해상도 / FPS | **1920×1080 / 60**, 720p·1440p·4K 등 / 59.94·50·30 등 |
| 색 공간 | **Rec.709**, Rec.601, Rec.2020 (SDR 변환 행렬) |
| 색 범위 | **Limited**, Full |
| 입력 HDR / 최대 밝기 | **SDR**, HDR10 / PQ → SDR, HLG → SDR · **1000** nit |
| 소리 | 장치에 오디오 핀이 있으면 거기서, 장치가 보내는 형식 그대로 · **음소거** |

설정은 자동 추측하지 않고 선택한 값으로 장치를 열고 YUV→RGB 변환합니다. 장치가 지원하지 않는 조합이면 오류를 표시하며 다른 형식으로 몰래 전환하지 않습니다. RGB 입력에는 YUV 행렬/범위 선택이 영향을 주지 않습니다. Rec.2020은 HDR 톤 매핑을 뜻하지 않습니다. 선택 후 **바탕화면 적용**을 눌러야 반영되며 설정은 다음 실행에도 유지됩니다. 현재 설정 목록은 공통 프리셋으로, 장치별 지원 모드 자동 조회는 아직 없습니다.

Live Gamer BOLT는 우선 **NV12 / 1920×1080 / 60 / Rec.709 / Limited / Input resolution**로 사용하세요. 검정이 뜨거나 어두운 부분이 뭉개지면 실제 소스에 맞게 색 범위를 변경하세요. 캡처보드가 4:3 소스를 16:9 프레임에 필러박스로 담는다면, **표시 비율**을 `Output resolution` + `Fill, cropping the overflow`로 두면 그 여백이 떨어집니다.

### 소리

기본값은 음소거입니다. **Mute**를 해제하면 소리가 납니다.

캡처 장치의 소리는 장치 자체에서, 영상 옆 핀으로 함께 나옵니다. 따로 고를 것이 없습니다. 장치가
소리를 보내면 언제나 받아두고 체크박스로 끄기만 하므로 전환이 즉시 이루어집니다 — 필요할 때만
받도록 하면 누를 때마다 캡처를 다시 시작해야 합니다. 모든 장치가 소리를 보내지는 않습니다. 가상
카메라는 영상만 보냅니다. OBS의 가상 카메라에는 오디오가 없고 짝이 되는 오디오 장치도 만들지
않습니다. 그런 장치에서는 체크박스가 비활성으로 바뀌고 마우스를 올리면 이유를 알려줍니다. OBS
장면의 소리를 들으려면 OBS 오디오를 가상 오디오 장치로 내보낸 뒤 그것을 소리 입력으로 잡으세요.

소리 형식도 픽셀 형식과 같은 이유로 엔진에 맡기지 않고 명시합니다. 핀은 여러 레이아웃을 제공하고
엔진은 요청과 맞는 것 중 첫 번째를 집으므로, 채널 수 없이 레이트만 요청하면 아무것도 요청하지
않는 것보다 나쁩니다. 7.1도 제공하는 카드라면 `48000`에 맞는 첫 형식이 8채널짜리이고, 2채널이
8채널로 들어옵니다. 2채널을 레이트와 함께 명시적으로 요청합니다.

샘플 레이트를 고르는 항목은 일부러 두지 않았습니다. 엔진에 2채널만 요청하고 레이트는 말하지
않으면, 엔진은 핀이 제공하는 첫 형식을 집습니다. 그게 장치가 자기 목록 맨 앞에 놓는 값이고,
카드는 들어오는 신호가 바뀌면 그 순서를 바꿉니다. **아무 말도 하지 않는 것**이 장치의 답을 쓰는
방법입니다. Live Gamer BOLT(GC555) 관찰: 44.1kHz 소스에서는 44100이 맨 앞·48000이 다음이고,
카드가 내려서 변환하는 96kHz 소스에서는 48000이 맨 앞입니다. 두 경우 모두 정확히 그 값으로
열렸습니다.

대신 채널 수는 반드시 말해야 합니다. 빼면 엔진이 전체 첫 형식을 집는데, 7.1도 제공하는 카드에서는
그게 8채널짜리일 수 있습니다. 2채널이 8채널로 들어오는 것이 "소리가 이상하다"의 대부분입니다.

레이트가 어긋나면 실패하는 게 아니라 **속도가 틀어진 소리**가 납니다. 같은 카드를 44.1kHz 소스로
두고 48000을 강제한 실측: 44100 샘플을 초당 보내면서 48000이라고 표기해 10초 분량이 9.19초 만에
도착했습니다 — 8.8% 빠르고 정확히 44100/48000입니다. 이를 보정하지 않기 때문에, 레이트는 누가
고르는 값이 아니라 장치가 말하는 값입니다.

그 뒤에 소스가 레이트를 바꾸면 — 이 곡은 44.1kHz, 다음 곡은 48kHz 같은 경우 — 알아서 따라갑니다.
핀은 협상한 레이트를 그대로 들고 있으므로 엔진을 다시 열어야 하고, 소리가 영상과 같은 입력을 쓰니
양쪽이 함께 열립니다. 그동안 화면은 **마지막 프레임에서 1.5초쯤 멈춥니다.** 검게 되거나 바탕화면이
비치지는 않습니다. 창과 스왑 체인은 그대로 두고 그 아래 엔진만 갈아끼우기 때문입니다.

소스가 바뀐 것은 두 가지가 알려줍니다. 하나는 **초당 도착량**이 핀이 주장하는 레이트와 어긋나는
것으로, 카드가 예전 레이트를 새 라벨 아래 계속 보내는 경우를 잡습니다. 이미 손에 있는 데이터라
공짜입니다. 다른 하나는 **장치의 형식 목록**입니다. 장치는 지금 받고 있는 것을 목록 맨 앞으로
옮기고, 캡처 중에도 답합니다 — 이 프로세스 안에서 약 8밀리초, 2초 간격, 띄우는 프로세스 없음.
실제로 일하는 건 이쪽입니다. 카드가 핀 레이트에 맞춰 리샘플하면 초당 바이트는 정확히 맞으면서
소리만 망가지므로, 장치만이 압니다. 답하지 않는 장치는 다시 묻지 않으며, 그 경우 소리는 재생을
시작할 때 협상한 값을 그대로 유지합니다.

Live Gamer BOLT에서 44.1kHz·48kHz·96kHz를 오가며 실측: 전환 3회, 재개방 3회, 화면이 멈춘 시간
1.6초·1.5초·1.7초, 그 사이 오탐 0건. 96kHz 소스는 핀이 48000이면 재개방이 필요 없습니다. 카드가
정확히 그 값으로 내려서 변환하기 때문입니다.

영상과 소리는 서로 다른 경로로 오므로 샘플 단위로 맞물려 있지 않습니다. 소리 버퍼는 캡처 버퍼
값을 따릅니다. 화면의 안정성과 지연을 맞바꾸는 그 값입니다.

### 배치

| 설정 | 선택지 / 기본값 |
| --- | --- |
| 표시 비율 | **Input resolution**, Stretch to screen, Output resolution |
| 출력 크기 / 매핑 | 예: `2753x2064` · **Fill, cropping the overflow**, Fit / Centre at 1:1 / Stretch to fill |
| 화면 위치 | 3x3 그리드, **Center** |

이 셋은 두 입력 모두에 해당하며 어느 쪽에서도 계속 보입니다. 캡처는 선택한 해상도를 기준으로,
동영상 파일은 파일이 실제로 어떤 모양인지를 기준으로 배치합니다. 후자는 파일을 고르는 즉시 동봉된
FFmpeg로 읽어내며, 아나모픽 픽셀도 반영합니다.

**표시 비율**은 프레임을 바탕화면에 올리기 전에 어떻게 처리할지 정합니다.
`Input resolution`은 그대로 둡니다. `Stretch to screen`은 모니터를 가득 채우며 그러느라 왜곡됩니다.
`Output resolution`이 OBS처럼 동작하는 쪽입니다. `2753x2064` 같은 크기를 주면 **원본 해상도가
무엇이든** 그 크기로 나옵니다. 1920x1080으로 잡든 3840x2160으로 잡든 결과는 2753x2064이고,
들어간 디테일의 양만 달라집니다. **출력 매핑**이 프레임을 그 사각형에 어떻게 넣을지 정하며,
안에서는 언제나 가운데 정렬입니다:

- `Fill, cropping the overflow` — 출력 전체를 덮을 때까지 키우고 넘치는 부분을 잘라냅니다. 왜곡도
  없고 빈 자리도 없습니다. 필러박스를 떼는 게 이겁니다. 4:3 소스를 3840x2160으로 캡처하면
  `2880x2160`을 x=480에서 잘라내는데, 여백이 끝나는 바로 그 지점입니다.
- `Fit, padding the gap` — 프레임 전체를 유지한 채 출력 안에 들어갈 때까지 줄입니다. 모양이 맞지
  않으면 잘리는 대신 빈 자리로 드러납니다.
- `Centre at 1:1, padding the gap` — 전혀 확대·축소하지 않습니다. 출력이 허용하는 만큼만 프레임
  가운데에서 가져와 소스 1픽셀을 화면 1픽셀로 그립니다. 원본에 없는 픽셀을 만들어내지 않으므로
  1920x1080 프레임은 출력을 더 크게 잡아도 1920x1080에 머뭅니다.
- `Stretch to fill, distorting` — 프레임 전체를 출력에 정확히 늘려 붙입니다. 필러박스 대신 소스를
  프레임에 눌러 담는 구형 캡처보드용입니다. 뗄 것이 없고 비율만 되돌리면 되는 경우입니다.

빈 자리는 검게 칠하지 않고 아예 덮지 않으므로 원래 바탕화면이 비칩니다. 모니터보다 큰 출력은
모양을 유지한 채 줄여서 맞춥니다.

설정 아래 줄이 지금 숫자가 무엇을 하는지 — 프레임에서 무엇을 잘라내 얼마나 크게 어디에 그리는지 —
그대로 보여주므로 어느 쪽으로 읽히는지 짐작할 필요가 없습니다.

**화면 위치**는 3x3 그리드로, 캔버스 크기 조정의 기준점처럼 읽습니다. 출력 사각형을 모니터의
어디에 놓을지 정하며, 그 사각형 안쪽은 언제나 가운데 정렬입니다. 남는 자리가 있어야 의미가 있으므로,
없으면 그리드가 비활성으로 바뀝니다 — 16:9 원본을 16:9 모니터에 통째로 올리면 이미 전부 덮고 있고, 화면에 늘린 경우도 마찬가지입니다. 동영상 모드에서는
파일을 고르기 전까지도 비활성입니다. 그때까지는 배치할 모양 자체가 없기 때문입니다. 자르기 자체는
언제나 프레임 가운데에서 가져옵니다. 필러박스는 여백을 양옆에 두기 때문입니다.

`Input resolution`과 `Stretch to screen`은 원본 모양이 모니터와 같을 때 — 대개의 경우 — 결과가
같습니다. 다를 때 갈라집니다. 16:9 모니터 위의 640x480 캡처는 전자에서 왜곡 없이 4:3으로, 후자에서
화면을 채우도록 늘어납니다.

고정 16:9 / 4:3 항목은 없습니다. 자르기 기준에서는 출력 해상도를 어설프게 적은 것에 불과하고,
고정 비율이 필요해지는 날이 오면 그건 자르기가 아니라 늘리기로 필요할 것이기 때문입니다.

캡처의 자르기는 캡처 엔진에서 일어나므로 여백이 애초에 파이프를 타고 오지 않습니다. 동영상의
자르기는 플레이어에서 하며, 어차피 디코더가 프레임 전체를 넘겨주므로 추가 비용이 없습니다.

그림이 덮지 않는 부분에는 **아무것도 그리지 않습니다.** 앱 창 자체가 그림 크기만큼만 있어서, 남는
영역은 원래 쓰던 바탕화면 그대로입니다. 검은 여백이 생기지 않으니 주변에 뭘 둘지는 Windows에서
직접 정하시면 됩니다.

OBS의 장면/데스크톱을 사용하려면 OBS에서 가상 카메라를 시작하고 해당 장치를 선택하세요. 네이티브 데스크톱 캡처 입력은 아직 구현하지 않았습니다. 자기 바탕화면을 캡처하면 반복 화면이 발생하므로 다른 모니터나 창을 소스로 사용하세요.

## 빌드

Windows x64와 .NET 8 SDK 필요. 최초 빌드 전에 캡처 엔진을 준비합니다. 배포 폴더에는 VLC와 FFmpeg가 포함되므로 사용자는 별도 설치가 필요하지 않습니다.

```powershell
./scripts/setup-capture.ps1
dotnet run --project Wallcast
dotnet publish Wallcast -c Release -r win-x64 --self-contained true -o artifacts/Wallcast
```

프로젝트 로컬 SDK가 있으면 `dotnet` 대신 `.\.tools\dotnet\dotnet.exe` 사용. 배포 시 `artifacts/Wallcast` 폴더 전체가 필요합니다. 단일 exe 배포가 아닙니다. publish는 빈 폴더에 하세요. 기존 폴더에 덮어쓰면 프레임워크 어셈블리가 패키지 버전보다 최신 타임스탬프를 가진 경우 교체되지 않아, 실행 시 `System.Text.Json` 로드 실패가 납니다.

### 릴리스 만들기

```powershell
./scripts/package.ps1
```

빈 `artifacts/Wallcast`에 publish한 뒤 `artifacts/Wallcast-v1.1.0-win-x64.zip`으로 묶습니다.
약 164MB이고 이 파일 하나만 올리면 됩니다. 이름에 들어가는 버전은 방금 빌드한 바이너리에서 읽어오므로
둘이 어긋날 수 없습니다. 이름 → 버전 → 플랫폼 순인데, Node와 PowerShell이 배포 파일에 쓰는 순서입니다.
풀면 `Wallcast` 폴더 하나가 나오고 어디서든 실행됩니다. 설치 과정도, 따로 설치할 것도 없습니다. 캡처 엔진·VLC 런타임·라이선스 파일 중 하나라도 빠지면 스크립트가
패키징을 거부합니다.

publish 시 VLC 패키지가 같이 담는 x86·arm64 런타임을 지웁니다. x64 전용 빌드는 절대 못 쓰는데
642MB 중 244MB를 차지합니다. 압축은 Windows 10·11에 기본 포함된 `tar.exe`로 합니다.
`Compress-Archive`는 항목 이름을 역슬래시로 쓰는데, macOS·Linux의 unzip이 이걸 파일 하나당 긴
이름 하나로 만들어버립니다.

버전은 `Wallcast/Wallcast.csproj`의 `<Version>` 한 곳에만 둡니다. 여기서 제목 표시줄, 트레이 툴팁,
exe 파일 속성까지 갑니다. 빌드가 커밋 해시도 붙이므로 제목 표시줄 스크린샷만 있으면 어떤 빌드인지
정확히 알 수 있습니다. 릴리스에는 태그를 맞춰 다세요: `git tag -a v1.1.0 -m "Wallcast v1.1.0"`.

FFmpeg와 LibVLC가 GPL이므로 이들을 담은 배포물도 전부 GPL입니다. 그래서 `LICENSE`와
`THIRD-PARTY.txt`를 publish 폴더에 같이 넣습니다. 후자에 구성 요소별 라이선스와 소스 위치가
적혀 있습니다. 배포하는 아카이브에는 둘 다 반드시 포함하세요.

## 범위와 구조

- `Sources.cs`: 파일/캡처 입력 모델.
- `Placement.cs`: 출력 해상도, 매핑 방식, 화면 기준점. 공용이므로 같은 모양의 동영상과 캡처는 같은 계산으로 배치됩니다.
- `Playback.cs`: 입력별 재생 경로 선택, LibVLC 동영상 재생, 이음매 없는 반복, 플레이어에 넘기는 자르기와 표시 비율, 오류와 자원 정리.
- `VideoProbe.cs`: 동봉된 FFmpeg로 동영상 파일의 표시 크기를 읽어, 파일도 캡처처럼 배치할 수 있게 합니다.
- `SoundStream.cs`: 엔진의 stdout을 쓰는 속도 그대로 읽어, 엔진이 플레이어를 기다리지 않게 하고 장치가 실제로 보내는 양을 셀 수 있게 합니다.
- `SoundFormats.cs`: 장치에 소리 핀이 무엇을 제공하는지 이 프로세스 안에서 묻습니다. 아무것도 띄우지 않고 소스 레이트 변화를 따라가기 위한 것입니다.
- `CaptureOptions.cs`: 픽셀 형식·해상도·FPS·YUV 변환, 그리고 캡처보드의 검은 여백을 떼어내는 자르기. 기하 계산 자체는 `Placement.cs` 담당입니다.
- `CapturePlayback.cs`: FFmpeg DirectShow 입력, 명시적인 색 변환, 최신 프레임 유지. 장치가 소리를 보내면 같은 프로세스의 stdout으로 WAV가 나오고, 그 스트림을 그대로 재생합니다. 프레임은 이름 있는 파이프로 받습니다. 리디렉션된 stdout 파이프는 버퍼가 작아 약 800MB/s에서 막히는데, 4K 60fps BGRA는 2.0GB/s가 필요합니다.
- `CaptureSurface.cs`: BGRA 프레임을 DXGI 플립 모델 스왑 체인으로 출력하고 비율을 유지합니다. 확대/축소는 GPU가 처리합니다.
- `DesktopHost.cs`: Windows Explorer WorkerW에 영상 창 연결.
- `CaptureDevices.cs`: DirectShow 비디오 장치 검색.
- `MainForm.cs`: 설정, 모니터 선택, 트레이, 로컬 설정 저장.
- `scripts/package.ps1`: 깨끗하게 publish하고 릴리스 zip으로 묶습니다. 라이선스나 캡처 엔진이 빠진 빌드는 패키징을 거부합니다.
- `scripts/make-icon.ps1`: `Wallcast.ico`를 그립니다. 큰 그림을 줄이면 아이콘 실루엣 두 개가 뭉개져서
  크기마다 따로 그립니다. `-PngDirectory`를 주면 PNG로도 내보냅니다.

설정은 `%LOCALAPPDATA%\Wallcast\settings.json`에 저장합니다. 앱 시작 시 자동 재생하거나 Windows 시작 프로그램에 등록하지 않습니다. 다중 모니터 동시 재생, 편집기, 웹 배경, 워크숍은 포함하지 않습니다.

바탕화면에 붙는 Explorer 창에는 GDI 리디렉션 표면이 없습니다. 그래서 그 안에서는 GDI로 그린 픽셀이 화면에 합성되지 않으며, 영상(LibVLC의 Direct3D11 출력)과 캡처(위 스왑 체인) 모두 D3D 경로로만 표시됩니다. 캡처를 GDI로 그리면 프레임이 정상적으로 들어오고 컨트롤이 칠해져도 바탕화면에는 아무것도 나오지 않습니다.

WorkerW 방식은 공개된 Windows 바탕화면 API가 아니므로 Windows/Explorer 버전에 따라 동작 차이가 있습니다. Explorer 재시작이나 모니터 구성이 바뀌면 재생을 중지하고 재적용을 안내합니다. DirectShow에 노출되는 장치만 지원하며 제조사 전용 SDK만 지원하는 장치는 대상이 아닙니다. 같은 이름의 장치 여러 개는 구분을 보장하지 않습니다.

## 수동 검증

자동 검증은 `dotnet run --project SmokeTests -c Release -r win-x64 --self-contained true`로 실행합니다. VLC 로딩, 장치 검색, 잘못된 입력, 출력 해상도와 매핑 네 가지, 화면 위치, 같은 모양의 동영상과 캡처가 똑같이 배치되는지, 실제 FFmpeg의 NV12 빨강/파랑 변환, Limited/Full, Rec.709/601 차이, 재생 정리를 검사합니다.

- 짧은 영상이 끝난 뒤 반복되는지, 음소거 전환과 중지가 되는지.
- 바탕화면 아이콘과 컨텍스트 메뉴가 정상 작동하는지.
- 보조 모니터 및 서로 다른 DPI에서 선택한 화면에 맞게 표시되는지.
- 캡처 장치/OBS 가상 카메라 적용, 장치 분리, 다른 앱의 장치 점유 시 오류 처리.
- 입력 전환, 트레이 숨김/복원/종료 후 장치 해제 및 원래 배경 복원.
- Explorer 재시작, 모니터 분리 후 재적용 안내.

동영상은 LibVLCSharp/VideoLAN.LibVLC.Windows.GPL, 캡처 입력은 FFmpeg 9.0.1 Gyan essentials 빌드, 캡처 출력은 Vortice.Direct3D11을 사용합니다. `scripts/setup-capture.ps1`은 버전과 SHA-256을 고정합니다. `capture/LICENSE-FFmpeg.txt` 및 `capture/README-FFmpeg.txt`를 유지하세요.

바탕화면 출력 검증: `dotnet run --project SmokeTests -c Release -r win-x64 --self-contained true -- --desktop "Live Gamer BOLT"`. 장치를 열어 바탕화면에 붙이고, 열린 창을 잠시 최소화한 뒤 실제 화면을 캡처해 수신한 프레임과 비교합니다. `--resolution`과 `--aspect`로 캡처 해상도와 표시 비율을, `--custom 2753x2064`로 출력 해상도를(`--pixels`면 `Centre at 1:1`, `--squeeze`면 `Stretch to fill`), `--anchor Left`로 화면 위치를 지정할 수 있고, 받은 fps와 화면에 나온 fps를 따로 보고합니다. 그림이 화면을 다 덮지 않으면 남는 영역이 원래 바탕화면과 같은지도 확인하고, 그중 몇 개가 원래부터 검지 않았는지 같이 알려줍니다. 바탕화면이 검으면 정상 동작과 검은 여백을 구분할 수 없기 때문입니다. `artifacts/desktop-capture.png`에 그때의 화면을 남깁니다. 창을 최소화했다가 되돌리므로 자동 검증에는 포함하지 않습니다. 프레임 수신만으로는 화면 출력이 증명되지 않기 때문에 필요한 검사입니다.

이 검사는 최소화되지 않고 남은 창의 영역을 빼고 비교하며, 가려지지 않은 영역이 20% 미만이면 실패가 아니라 SKIP입니다. 움직이는 소스에서는 화면을 찍는 순간과 프레임을 받는 순간이 어긋나므로 앞뒤로 받은 여러 프레임 중 가장 잘 맞는 것과 비교합니다. 둘 다 없으면 렌더러가 멀쩡해도 실패로 보입니다.

동영상 출력 검증: `dotnet run --project SmokeTests -c Release -r win-x64 --self-contained true -- --video`. 단색 좌우에 240px 검은 여백을 둔 2초짜리 클립 — 이 앱이 떼어내려는 바로 그 필러박스 — 을 만들어 바탕화면에 올리고, 10초 동안 반복 다섯 바퀴를 도는 내내 화면을 쉬지 않고 읽습니다. 그림이 아닌 읽기는 전부 구멍이며, 반복 지점의 구멍이 이 검사의 존재 이유입니다. 멈췄다 다시 시작하는 옛 방식은 1176번 중 117번이 비어 있었고, 입력 반복 방식은 1201번 중 0번입니다. 배정받은 창 안에서 그림이 어디까지 닿는지도 재기 때문에, 잘리지 않은 여백과 바탕화면이 비치는 빈틈을 모두 잡아냅니다. `--custom 1440x1080`으로 출력 해상도를(나머지 세 매핑은 `--pad`, `--pixels`, `--squeeze`), `--aspect`와 `--anchor Left`는 위와 동일하게, `--seconds`로 클립 길이를 지정하고, `--video` 바로 뒤에 경로를 주면 그 파일을 재생합니다. 이 경우 기하는 보고만 하고 판정하지 않습니다. 그때의 화면은 `artifacts/desktop-video.png`에 남습니다. 캡처 검사와 마찬가지로 창을 최소화하므로 자동 검증에는 포함하지 않습니다.

화면 검증: `dotnet run --project SmokeTests -c Release -r win-x64 --self-contained true -- --ui-preview`. 설정 창을 두 입력 모드 모두에서 `artifacts/settings-capture.png`, `artifacts/settings-video.png`로 그려냅니다. 어느 한쪽에서 배치 설정이 사라지거나, 동영상 모드에 캡처 설정이 나오거나, 비활성화된 화면 위치 그리드가 이유를 달고 있지 않으면 실패합니다.

처리량 검증: `dotnet run --project SmokeTests -c Release -r win-x64 --self-contained true -- --bench "Live Gamer BOLT"`. 1080p·1440p·4K에서 실제로 받은 초당 프레임과 MB/s를 보고합니다. 장치가 내보내는 속도보다 느리면 그 차이만큼 프레임이 큐에 쌓여 지연이 됩니다. 지연 문제는 여기서 먼저 확인하세요.

소리 경로 검증: `dotnet run --project SmokeTests -c Release -r win-x64 --self-contained true -- --sound "Live Gamer BOLT"`. 앱의 실제 재생 경로를 그대로 돌립니다. 소리와 함께 바탕화면에 올리고, 돌아가는 중에 음소거를 켰다 끄고, 중지에 걸리는 시간을 잽니다. 시간 재는 게 요점입니다. 플레이어가 엔진의 stdout을 읽는데, 그 읽기는 데이터가 오거나 쓰는 쪽이 사라져야 돌아옵니다. 순서를 잘못 잡으면 아무도 응답하지 않을 읽기에 UI 스레드가 묶입니다. 엔진을 먼저 끝내며, 중지는 1초를 한참 밑돌아야 정상입니다.

## 라이선스

GPL-3.0-or-later. [LICENSE](LICENSE) 참고.

선택의 여지가 있는 부분이 아닙니다. 동봉된 FFmpeg는 `--enable-gpl --enable-version3`로 빌드됐고 동봉된 LibVLC도 GPL 빌드입니다. 따라서 배포물 전체에 GPLv3 의무가 따르며 해당 구성 요소의 소스 제공도 포함됩니다. 허용적 라이선스를 쓰려면 두 바이너리를 동봉하지 않아야 합니다.

UI와 앱 메시지는 영어입니다. 이 문서는 한국어판이고 표준 문서는 [README.md](README.md)입니다.
